# DeepGEMM 开发规范

[English](development.md) | 简体中文

本规范适用于本仓库的贡献，包括由编程代理完成的修改。修改前应阅读现有实现及相关 API、JIT、scheduler 和测试代码。除非接口变更已经明确评审，否则应遵守既有契约。

## 范围与架构

- 修改应聚焦于要求的算子、平台和行为。无关清理、环境补丁、新功能与 kernel 优化应分别处理。
- 使用 `csrc/` 下的 C++ JIT 路径，以及 `deep_gemm/include/deep_gemm/` 下的设备实现。原 Python JIT 实现已删除，不应恢复或作为实现依赖；当前实现仍在使用的 Python API、工具和测试继续维护。
- 公共 API 的校验和注册放在现有 API 层；配置选择、tile 规则和资源计算放在对应 heuristics 层；执行编排放在 runtime 实现中。
- API 设计和参数检查应参考上游开源 DeepGEMM，尽量对齐上游的接口签名、参数含义、校验行为和输出语义。因 PPU 架构差异，可以调整 API 或新增 PPU 专有 API；应说明与上游的差异及其架构原因。
- 当现有 copy 原语、scheduler、预处理和 helper 能满足语义及代码生成要求时，应直接复用。确需自定义原语时，应说明具体差异，并提供生成代码或实测证据。
- 共享公共计算逻辑，用少量 policy 或 helper 隔离必要差异。避免复制完整 mainloop、增加大量公共包装接口，或用单个策略开关绑定互不相关的优化。
- 不同 dtype 的配置逻辑保持独立。确需共享的参数类型应移到适当的公共位置，不应仅为获取间接依赖而包含另一个算子的实现。
- 能在算子自身 runtime 内解决的问题，不应为了该算子修改公共 compiler、cache 或 runtime 接口。跨模块修改需要明确理由，并验证受影响的调用方。

## 优化结构与取舍

针对 AI 贡献者：性能优化探索阶段可以并且鼓励尝试所有可能的路径，包括专用配置、重复代码和临时策略；此阶段不受下述泛化和结构要求约束。但优化必须归因，通过受控对照分别确定每个优化点的具体提升或回退，不能只报告多个改动叠加后的总收益。准备正式提交时，再按照以下要求选择、收敛和整理保留的改动。

- 泛化应将实验分支收敛为少量具有不同数据流或资源需求的策略，不应将历史实验中的所有开关、buffer 数量和备用路径都保留在正式实现中。
- 公共计算只表达一次，将差异放在实际发生的位置，例如路由索引、操作数加载或 fragment 生命周期。通过小型 policy 或 helper 表达这些差异，不为每个接口或 tile 复制完整 mainloop。
- 配置选择、资源计算、路由准备和执行使用同一份解析后的计划。heuristics 选择计划，runtime 组织执行，kernel 消费计划；避免各层独立重建配置或隐式重新选择策略。
- 是否保留优化，应同时考虑实测收益、支持的工作负载范围和维护成本。性能接近时，优先选择分支更少、约束更清楚、资源需求更低的方案。为简化通用实现，可以接受部分 case 的小幅性能损失。
- 只有各实现都具有明确、值得维护且其他方案无法充分覆盖的适用范围时，才保留多种实现。说明选择边界及新增代码和验证成本；若选择结果或实测收益已无实质差异，应合并或删除相关策略。
- 泛化不要求每个 case 都加速。应报告最大回退、受影响的工作负载和整体收益，供评审取舍。专用配置应结合维护成本和通用策略的质量一起评估。
- 完整清理未保留的实验，包括无用开关、配置字段、helper 及其专用测试和文档。实验依据保留在本地记录中，不在正式实现中留下没有受支持用途的闲置路径。
- 正式测试聚焦接口契约，以及有代表性的策略切换、尾块和资源边界。大范围性能探索放在离线工具中；实现合并或删除时，同步精简重复测试，同时保留不同的行为覆盖。

## 配置与分发

- 配置选择应是确定的，依据 host 已知的 shape、已说明的 hint、配置的计算资源和设备能力。允许为已调优的工作负载使用性能查找表，但必须同时维护能够覆盖表外工作负载的通用策略。在代表性工作负载上，将通用策略与精确调优配置比较，保持性能差距合理，并报告典型和最大差距供评审；不能依靠查找表掩盖薄弱的通用路径。kernel 和启发式修改也应维护通用路径，并在禁用查找表覆盖的情况下独立验证。
- 生产分发不得在 GPU 上实测候选 kernel 来选择路径。不使用计时校准、候选试跑、为调优进行的 device-to-host 同步，或实测成本系数缓存。离线调优工具与生产分发分开。
- 遵循现有由调用方选择 device 和 stream 的约定。未经仓库级需求评审，不在个别 API 中增加自动设备切换。依赖设备的资源检查也应遵守同一约定。

## Graph replay 与并发

- Graph replay 应正确使用更新后的输入，不得错误复用依赖旧输入内容的缓存结果。
- 使用共享 workspace 或内部 stream 时，应保证并发安全、执行依赖及资源生命周期正确。

## 数值与功能正确性

- API 和实现路径允许覆盖不全，但不允许静默出错。应明确说明支持范围，对不支持的输入或参数组合明确报错，不得静默产生错误结果。
- 明确输入格式、scale 语义、布局、输出顺序、对齐、支持的维度及 mask 行为。对于 masked 输入，区分分配容量、有效行数和预期工作量 hint。
- 除非数值变更已经明确评审，否则保持计算顺序和舍入行为。不通过放宽容限使优化通过。参考结果应根据实际量化输入和声明的 scale 语义计算。
- 尽可能在预处理阶段完成成本较高的静态属性校验，避免每次 GEMM 都扫描不变的权重。保持既有预处理契约，对不支持的值明确报错。
- 根据改动覆盖非均匀专家、空专家、尾块、token 重复使用、路由变化及无效输出区域。布局修改应使用单点或结构化输入验证；随机整体误差可能掩盖排列错误。
- 新执行路径必须考虑既有标量选项和输出语义。不支持的组合应说明并评审，不得静默忽略参数或丢失已有 API 能力。

## 验证与性能证据

- 新增或修改 API 时，应在 checkin list 中添加对应 UT。UT 数量尽量少而精，覆盖关键行为，避免重复 case。
- 新 API 应接入本仓库的 UT dump/replay 工具，replay 至少覆盖常用执行路径，不要求覆盖所有路径。允许部分 device 侧参数无法 dump，但应说明这些限制及支持的 replay 范围。
- 新 API 应遵循仓库现有日志约定，在启用 `show_log` 时打印 kernel 信息，包括实际选择的执行路径、tile 配置及适用的资源信息。
- 优化目标和特化条件必须考虑实际应用行为及支持的调用契约。允许针对特定场景优化，但该场景应在实际应用中合理存在，并有调用逻辑或代表性路由数据等依据。不能仅因合成测试构造了某种条件，就为实际几乎不可能走到的场景增加特化。例如，专家行数均衡不代表 fused gather 中的 token ID 等间隔排列；不得把 cyclic 或均匀排列的测试路由当成生产不变量。
- 修改 `csrc/` 后必须重建 host 扩展。仅修改设备代码时，也应确认 JIT 使用了预期源码和配置。远端验证需核对实际加载的包与同步后的源码。
- 性能测量前先验证功能和精度，使用空闲设备，不干扰其他任务。
- 区分有效 GEMM 利用率、实际发射的 tensor 工作量与 profiler 计数。

## 文档与提交

- 提交 PR 时必须关联对应的 issue。
- API 变动时应更新 README 和 CHANGELOG；复杂 API 可以在 `docs/api/` 下添加详细说明文档。API 或行为变化应更新相关现有测试，准确说明限制和性能结论。正式 README 和发布说明使用 M890 等公开产品名称；代码可保留既有内部架构标识。
- 发布说明只描述对应 commit 的修改。说明优化解决的问题及执行方式的变化，commit message 聚焦改动和验证结果。
- 本地实验、profiler 报告、构建产物、机器专用设置、`tmp/` 产物及未要求提交的 example 不进入 commit。commit message 不包含机器名或设备标识；验证日志中保留这些来源信息。
- 提交前检查完整 diff，清理过时的实验接口，并确认文档中的配置实际选择了所述计划。不发布未测量的性能结论，不以少量抽样宣称完整回归通过。

## 规范的应用

贡献者和编程代理应在实现或评审前阅读本文，并结合明确的任务指令及已批准的 API 契约处理冲突。本文是开发指导，不是自动检查机制。公共配置格式、执行拓扑、数值验收标准和共享基础设施的变更，应先评审再实现。
