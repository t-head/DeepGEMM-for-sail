# Native W4A8 on PPU0015

The public NoPad, Masked and Fused APIs use packed E2M1 weights with group-32
UE8M0 scales, per-row E4M3 activations, FP32 accumulation and BF16 output.
Prepare weights and scales with
`preprocess_weights_and_scales(PreprocessMode.W4A8_MXFP4_MMA, ...)`, and apply
the returned inverse scale exactly once to activation scales.

## Organization

| Layer | Source | Responsibility |
| --- | --- | --- |

| Streamed runtime | `csrc/jit_kernels/impls/w4a8_streamed_gemm.hpp` | Partial decoded buffers, events, streams and capture readiness |

## Native strategies

The existing native configuration remains the default. Wider M tiles reuse
one decoded weight fragment across more output rows. Short-K configurations
retain their existing N expansion, resident activation tiles and split-K behavior.

Compact selection covers mean row counts up to 511, subject to resource
checks and the precedence of wider native or Routed kernels. This includes the
intermediate R=65..95 range. NoPad uses a warp prefix for at most 64 experts:
M16 pairs tasks, M32 shares prefix storage, and M64 retains the warp prefix.
Larger NoPad expert sets reuse the stock scheduler and its preprocessing layout.
Fused reuses the public expert records for up to 1024 experts. Compact K32 fragments reduce live register state; M32 uses narrower N
tiles, while underfilled Fused M16 uses more N warps. Full-wave Fused M16 keeps
the default fragment strategy. Selection also requires aligned N/K, sufficient
K work, and shared-memory/thread capacity. It does not depend on model dimensions
or an exact device name/CU count.

The routed strategy amortizes a device metadata pass over expert sets
with moderate rows per expert. NoPad uses M160/M192 candidates; Fused uses M160
with a bounded activation operand ring. M16 tail counts limit unnecessary MMA work.
Small Fused expert sets require several waves to amortize metadata construction.
Selection rejects excessive M-tile padding, and adjacent Fused M blocks are
interleaved across N tiles and experts to balance full blocks and short tails.
The metadata pass compares actual expert row counts and constructs fresh work records on every call. Both paths
use the same native kernel, with scheduler adapters and bounded compile-time
fragment strategies. Resource calculations stay in the heuristics layer; the
runtime initializes dynamic shared memory before checking actual occupancy.
Compiled candidates exceeding the local-storage budget retain native execution;
the runtime caches that resource decision without caching input values.

For aligned R=257..511 calls with enough work, an adaptive native/wide
selection compares the original Default kernel with M160. The first ordinary
call prepares the native/wide candidates and measures their kernels and selection
overhead on the caller stream with two warmups and five event samples per
measurement. Live selection also requires its measured overhead to stay within
5% of the native kernel time. Otherwise, or when the wide gain does not repay
selection, subsequent calls use the original native path without per-call
selection. This conservative
choice may miss a benefit after the route distribution changes. This cold initialization synchronizes the
caller and caches a native/adaptive decision and two time-per-M-tile coefficients by device, dimensions, token
count, public configuration and configured CUs. It caches no input values.
Warm calls remain asynchronous. When adaptive selection is enabled, one GPU scan of the current expert rows computes
both padded tile counts, creates the wide work records, and selects one active
kernel. For NoPad with at least 128 experts it also creates the stock scheduler
table, avoiding duplicate preprocessing. Both conditional launches are part of
the API cost. Graph replay recomputes the choice from updated row counts. This
bounded model accounts for padding and measured reuse; it does not simulate
exact worker loads or guarantee the fastest strategy for every distribution.

For Fused, work records preserve the expert token offsets padded for the
original public config returned by `moe_align_block_size`. Internal M tiles do
not reinterpret that layout. Non-default configs and unknown token layouts
retain native execution. NoPad starts with activations already grouped by expert.
Masked and non-unit `inv_scale` retain their native behavior.

## Streamed decoding

Streamed decoding supports NoPad and default-layout Fused calls with sufficiently
large weight reuse. Eligibility uses dimension alignment, conservative rows per
expert, workspace size, and estimated chunk/wave overhead. Per-call device row counts
prune empty experts. The bounded plan decodes at most half the experts at once,
using two partial E5M2 weight buffers, each bounded by 384 MiB including row
metadata. Expert chunks are selected by a bounded wave/launch search under the
workspace and scheduler limits, rather than a fixed expert count. If one expert
exceeds the buffer budget, the same decoder/core pipeline iterates over
N256-aligned slices and writes the original output stride. N tails aligned to
64 are supported. Input values, routing values and decoded weights are never
cached across invocations.

Fused gathers activations and their row scales from the public padded token
layout into contiguous expert rows. The additional activation workspace is
bounded by 1 GiB. Short calls gather once on the caller stream before decoding;
longer calls gather each expert chunk inside its decoder, overlapping later
chunks with earlier computation. Partial-N calls gather once before the stream
fork, avoiding repeated writes to shared activation storage across N slices. The plan includes all gather, decode and join
work in the public call. Decoder register limits and chunk sizes preserve
co-residency with the FP8 core. Fused and NoPad share the decoder/core pipeline;
NoPad keeps its existing launch ABI and scheduling policy.

Events order decoding, computation and buffer reuse, then join the caller
stream. Ordinary warmup prepares modules, stream/event resources and readiness
for the actual caller and shape, and prepares its native fallback modules.
Capture on a different caller or an unwarmed Streamed plan uses that already
loaded native path before allocating a streamed buffer. Capture never compiles
or loads a W4A8 module from disk; a completely cold request fails with an
explicit instruction to warm it outside capture. Compile-only mode preserves
the existing native compiler/launch behavior. Adaptive selection similarly
requires coefficients and handles prepared outside capture, otherwise using
a prepared native path.

All successful native strategies preserve the operation parameters and HGTX
range controlled by `PPU_LIB_SHOW_PARAMS` and `PPU_LIB_PERF_INSTRUMENT`. Routed
instrumentation includes metadata construction. Configured CU counts are used
in launch planning.

## Validation and measurement

Use the SDK environment and build procedure in the repository README. Keep any
SDK compatibility conversion in a separate worktree.

`tests/test_w4a8.py` covers grouped modes, scales, explicit configs, empty and
uneven experts, shapes outside the initial tuning workloads, reduced configured
CU counts, and Fused metadata layouts. Streamed regressions cover ordinary and
new-stream execution, warmed Graph replay after activation/weight/scale updates,
routing changes that move empty experts, and capture following compile-only
warmup. Regressions also cover ordinary warmup followed by capture on a fresh
stream, multiple prepared plans, outputs beyond 2^31 elements, and partial-N
Graph replay with an oversized expert and N tails. Intermediate-R tests change
the distribution between balanced and concentrated after capture.

`tests/bench_w4a8.py` measures representative complete APIs using two output
addresses, 12 warmups, 15 rounds and 20 calls per round. Run the same driver
against each built revision using `PYTHONPATH`. Its optional profiler traces
separate main GEMM, metadata and decoding kernels; these durations use the
profiler's own timeline and can overlap. Host enqueue time is reported separately.
